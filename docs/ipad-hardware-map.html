Henge research · 8 November 2026

What the iPad can give the Mac, natively

Battery, volume, brightness, network, Wi‑Fi, Bluetooth, AirDrop, location, Touch ID and Apple Account, each checked against the drivers macOS actually ships for a virtual Mac.

The rule for this map

"Native" means macOS sees a piece of hardware and its own built-in driver handles it, the same way it does on a real Mac. No helper app drawing a fake battery icon, no extra install inside macOS.

The big finding

macOS already contains Apple's own drivers for virtual-Mac hardware that Henge doesn't emulate yet. One is a virtual battery. Others cover Touch ID, an Apple Account identity device, and a device for plugging in any USB-style input device. The virtual Mac's kernel also carries Apple's Wi‑Fi driver, its Bluetooth chip driver and its USB speaker driver. Henge builds its own hardware, so it can offer any of these, and macOS will treat them as real.

All of this was checked directly: in the macOS 15.6.1 virtual-Mac kernel downloaded from Apple, in the drivers on this Mac (macOS 27.0.1), and in Apple's own Virtualization framework.

Battery

Native · buildable

Apple built a battery device for virtual Macs, and macOS ships its driver (AppleVirtualPlatformPowerSource). Apple's Virtualization framework drives it with two values: charge and plugged in or not. It can also follow the host's own battery. Those are exactly the two things the iPad reports.

On the Mac
macOS's own battery: menu bar icon, Battery settings, and its battery behaviour (sleep timings, Low Power Mode "only on battery", warnings when low). Nothing installed inside macOS.
From the iPad
Battery level and charging state (public iOS API, read every few seconds).
Work
Add one new virtual PCI device to Henge (Apple ID 106b:1a07, a virtio device like the disk and network Henge already has). Learn its message format from Apple's driver and from Apple's own VM app on this Mac, the same way Henge learned the graphics protocol.
Unknown
Whether it draws the menu bar battery exactly like a laptop's. Apple's own code treats it as a battery, so this is very likely. The first test answers it.
Proof
Driver present in the macOS 15.6.1 virtual-Mac kernel. Apple's Virtualization framework has _VZMacSyntheticBatterySource (charge, connectivity) and _VZMacHostBatterySource.

Volume

Native · buildable

Your Bluetooth-speaker idea is the right model, and macOS supports it natively, but not through the sound device Henge uses today. Apple's virtual sound device does its volume in software inside the Mac: it makes the audio quieter before sending it out. Tying that to the iPad's volume would turn the sound down twice.

A USB speaker with its own volume control works the way you described. The Mac's slider and volume keys send "set volume to 40%" to the speaker, and the sound arrives at full strength. When the speaker's own knob moves, it tells the Mac, and the Mac's slider follows. Apple documents this in Technical Note TN2274.

On the Mac
An output called "iPad" (or the device's name). The menu bar slider, Control Center and volume keys all control the iPad's real volume. Pressing the iPad's volume buttons moves the Mac's slider, with macOS's own volume display.
From the iPad
Reading the system volume is public API. Setting it uses iOS's system volume control (the same one music apps embed).
Work
Henge already emulates a USB controller with a USB drive on it. A speaker needs one thing it lacks: steady streaming transfers (USB "isochronous" transfers). Then add the speaker itself, route Mac audio to it, and wire the volume both ways.
Proof
macOS's USB audio driver (AppleUSBAudio) is in the virtual-Mac kernel. Apple's VM sound plug-in contains a software volume processor (AVIOVolumeProcessor), which confirms why the current device can't do this.

Brightness

Native · needs a test first

Apple's virtual-display protocol has brightness built in. On this Mac, both Apple's Virtualization code and the paravirtual graphics framework carry display brightness settings (MinNits, MaxNits, setBrightnessCaps) and brightness change requests. When the virtual screen says "I have brightness from X to Y", macOS should show its normal brightness slider and accept the brightness keys, sending each change back to the host.

On the Mac
The Displays brightness slider, the Control Center slider and the brightness keys. Each sets the iPad's real backlight.
From the iPad
Screen brightness, read and set (public API).
Work
Henge implements this display protocol itself. On this Mac, turn on brightness in Apple's graphics framework, record what changes in the messages, and add the same to Henge.
Unknown
Whether macOS 15 guests already use it, or only newer ones. The recording answers it. Henge's current "dim the Mac's screen" slider stays as the fallback.

Network

Native · buildable

This is already native. Henge's network card is the one Apple uses for virtual Macs, and macOS lists it as Ethernet. The small native addition: when the iPad loses internet, the Mac sees the cable unplugged; when it comes back, the cable is plugged back in and the Mac reconnects at once. Henge already has the unplug/replug code (it's used after resuming a paused Mac).

Work
Days. Watch the iPad's connection and flip the virtual cable.

Camera and microphone

Native · buildable

Not on your list, but the same idea. macOS supports standard USB webcams with no install, so the iPad's camera can appear as a USB camera on Henge's USB controller. For the microphone, Apple's VM sound device already supports an input. Henge would add the input side.

On the Mac
"iPad Camera" in FaceTime, Photo Booth, Zoom and browsers; "iPad Microphone" in Sound settings.
Work
Weeks. The camera can use simpler USB transfers than the speaker, so it doesn't wait on the speaker work.

Touch ID from Face ID

Native · needs a test first

macOS 27 includes a Touch ID driver for virtual Macs (AppleVirtIOBiometrics, Apple ID 106b:1a0a), and Apple's Virtualization framework has a private Touch ID setting for it. The 15.6.1 virtual-Mac kernel does not have it, so this is for Tahoe or macOS 27 Macs.

On the Mac
Touch ID for unlocking, sudo, password fills and app prompts, answered by a Face ID scan on the iPad.
Unknown
Whether Apple's design needs the host Mac's security chip to sign the answer. If it does, an iPad can't stand in. Reading the driver answers it before any building.

Wi‑Fi

Native · big project

More possible than I first said. The virtual-Mac kernel ships Apple's full Wi‑Fi driver, and it will attach to any Broadcom PCI device (vendor 14e4), no special board wiring needed. If Henge pretends to be the Broadcom Wi‑Fi chip Macs use, macOS shows a real Wi‑Fi menu.

On the Mac
Wi‑Fi on, connected to one network: the one the iPad is on, by name. Traffic still flows the way it does today.
Why it's big
The chip's protocol isn't public. Asahi Linux and Linux's brcmfmac driver document most of it, but Apple's driver asks the chip far more questions than Linux does, and it normally reads calibration data that real Macs keep elsewhere. Expect months, with a real chance of a wall.
From the iPad
Only the current network's name, and only with Location permission plus Apple's Wi‑Fi information entitlement. iPad apps can't scan for other networks, so the list would hold one network.

Bluetooth

Native · big project

Also reachable. macOS has a driver (AppleConvergedPCI) for the Bluetooth half of Apple's Broadcom chips, matched by their PCI IDs, and Asahi Linux has documented that chip's protocol. The limit is the iPad: apps only get Bluetooth Low Energy (fitness sensors, some accessories) through Core Bluetooth. Classic Bluetooth, such as headphones and older keyboards, stays with iPadOS. Your AirPods already play the Mac's sound, because Henge's audio goes out through the iPad.

AirDrop

Native · big project

You're right that others have done it, but each owned the radio. Google's Pixel 10 speaks AirDrop because Google controls the phone's Wi‑Fi chip. OpenDrop on Linux needs a Wi‑Fi card put into a special raw mode. AirDrop uses Bluetooth Low Energy to find devices and Apple's own Wi‑Fi link to send files. An iPad app can use neither directly.

A design that still feels native, once Wi‑Fi and Bluetooth emulation exist: the emulated chips make the iPad appear as a nearby device in the Mac's own AirDrop window. Drop a file on it, and Henge opens the iPad's share sheet with that file so you can AirDrop it to anyone. Incoming works the other way: AirDrop to the iPad, choose Henge, and the Mac receives a normal AirDrop. This only makes sense after the Wi‑Fi and Bluetooth work.

Location

Native · buildable

Macs have no GPS chip of their own; macOS normally finds its location from nearby Wi‑Fi. But Macs do accept plug-in GPS receivers, and Henge can be one. It would show up as a USB GPS (the common u‑blox kind) and send the iPad's real GPS position in the standard format GPS receivers use (NMEA). macOS's built-in USB serial driver handles it with nothing installed.

Who sees it
Navigation, marine, flight and mapping software that reads GPS receivers directly (the apps people buy those dongles for). Maps, Weather, Find My and websites normally don't read a plain USB GPS.
Work
Small. A GPS sends only a few lines of text a second, using the same simple USB transfers as Henge's USB drive. The iPad's position comes from Core Location.
System-wide
macOS 27 has a second, hidden route. Its accessory service (accessoryd, Apple's CarPlay and MFi accessory protocol, iAP2) has a location feature that takes GPS sentences from an accessory, and Location Services has an "accessory location provider" that uses them. That would give every app the iPad's position. The catch: Apple only trusts accessories that pass MFi authentication, a signature from an Apple-issued chip that Henge can't produce. A short test will show whether macOS insists on it for location.
Last fallback
macOS's location simulation service (CLSimulationManager, what Xcode uses), fed with the iPad's GPS. Software, not hardware, and also untested.

Apple Account sign-in

No native path

The virtual Mac does have an identity device (106b:1a0c), the one that lets Apple's own VMs sign in. On a real host Mac, Apple's identity service gets a certificate from Apple for a key held in the Mac's Secure Enclave (Apple calls this Basic Attestation), and the VM's sign-in is vouched for with it. The strings in Apple's code spell this out: "host certificate", "attestation key", "BAA certificate refresh".

The Hackintosh trick worked because Intel Macs proved their identity in software, with serial numbers that could be copied. Apple Silicon Macs prove it with that security chip, and an iPad app can't get a Mac's certificate. Copying a real Mac's identity would also break Apple's terms and risks getting the Apple Account locked. The App Store's FairPlay device (106b:1a08) likely depends on the same host trust.

Other native pieces found along the way

Native trackpad. macOS ships a virtual multi-touch trackpad driver (AppleVirtIOInputTrackpad). Touch on the iPad could become real trackpad gestures that macOS handles itself (pinch, swipe between spaces, Mission Control), instead of the helper's scroll injection. Check with whoever is working on touch input before starting this.

Automatic setup (macOS 27). Apple's new provisioning device (106b:1a11) can create the user account during install, skipping Setup Assistant.

Plug-in input devices. Apple's HID bridge (AppleVirtualPlatformHIDBridge) lets the host present any keyboard-style device, such as volume and brightness media keys.

Suggested order

  1. Battery. Most visible, one new device, Apple's own driver.
  2. Network follows the iPad. Days of work, and it removes a confusing state.
  3. USB GPS receiver. Small, and it builds the USB-device groundwork the speaker and camera reuse. Test the system-wide accessory route at the same time.
  4. Brightness. Start with the recording on this Mac; build if macOS 15 responds.
  5. USB speaker volume. The streaming transfers it needs also help the camera and mic later.
  6. Camera and microphone.
  7. Touch ID. Read the driver first; build only if it doesn't need a Mac's security chip.
  8. Wi‑Fi, then Bluetooth, then AirDrop. A separate long research track, best started once the items above ship.
